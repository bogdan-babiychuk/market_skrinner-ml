# MarketScreener · Детектор локальных разворотов

> **Проектная карточка · модель ещё не обучена**  
> Получение данных проверено пользователем. Обучение, оценка качества и интеграция модели — следующие этапы.

**Обновлено:** 25 октября 2026 года  
**Проект:** учебный практикум MarketScreener  
**Компонент:** `turn-detection` · многоклассовая классификация временного ряда

## 1. Назначение

Модель должна обнаруживать возможные локальные развороты по рыночной истории одного инструмента и возвращать класс события вместе с вероятностями.

**Получатель ответа — слой принятия решений MarketScreener.** Он применяет дополнительные условия подтверждения и ограничения публикации, затем решает, формировать ли итоговый сигнал.

```text
Окно API → проверка данных → признаки → модель → адаптер
                                                      ↓
                                  Слой принятия решений MarketScreener
                                                      ↓
                                         Сигнал / отсутствие публикации
```

Адаптер — код преобразования ответа модели в согласованный формат. Он добавляет инструмент, время окна и сведения о версии.

**Предполагаемая польза:** дать системе дополнительную оценку события на основе сочетания цены, объёма и RD. Преимущество ML перед простым правилом нужно проверить экспериментом; конкретный критерий преимущества обсуждается. Сокращение задержки пока не выбрано как цель.

Модель не исполняет сделки. Автоматическая торговля и управление капиталом находятся за пределами учебного прототипа.

## 2. Вход и выход

### Вход: одно окно одного инструмента

| Параметр | Значение |
|---|---|
| Контракт | `model-window-64x6-v1` |
| Размер | **64 строки × 6 полей** |
| Шаг времени | 1 минута; строки от старых к новым |
| Поля по порядку | `rd_value`, `open`, `high`, `low`, `close`, `volume` |
| Привязка | `symbol` и время последней строки — `windowEndTimestamp` |

OHLC описывает цены свечи, `volume` — объём, `rd_value` — предоставляемый MarketScreener показатель RD. Его формула в изученных материалах не раскрыта. RD не является вероятностью модели.

**64 строки — глубина истории, а не горизонт прогноза.** Момент целевого события и допустимую задержку нужно определить отдельно.

### Выход: один класс и вероятности

| Класс | Код | Значение |
|---|---:|---|
| `TURN_UP` | 1 | Локальный разворот от снижения к росту |
| `NO_TURN` | 0 | Подтверждённый разворот не обнаружен |
| `TURN_DOWN` | −1 | Локальный разворот от роста к снижению |

Ответ сопровождается инструментом, временем окна, версиями модели и признаков. `NO_TURN` не означает отсутствие движения цены и не порождает BUY/SELL. Ошибка обработки фиксируется отдельным статусом.

## 3. Модель и признаки

Планируется классическая табличная ML-модель на CPU. Алгоритм выбирается после первых экспериментов. Окно преобразуется в одну строку признаков.

**Кандидаты в признаки:** изменения цены за разные периоды, волатильность, характеристики свечей, динамика объёма, лаги и скользящие характеристики RD.

Правила подготовки:

- При обучении и применении используется один и тот же код расчёта признаков.
- Каждый признак доступен не позже момента выдачи ответа.
- Обучаемые преобразования настраиваются только на train.
- Порядок признаков и нормализация фиксируются в `feature-schema.json`.

## 4. Обучающие данные и разметка

**Источник истории:** суточные CSV студенческой передачи MarketScreener. Время — Unix-миллисекунды UTC. Инструменты и период выбирает команда с обоснованием.

Сохраняются оригиналы CSV, контрольные суммы SHA256 и manifest состава. Пропуски, дубликаты, периодичность и исключения описываются в data-audit report. История из CSV не смешивается с динамическим `/training-dataset`, где RD может быть пересчитан.

> **`signal_barrier` исключается из всего ML-процесса:** признаков, меток, весов и фильтров строк. Допустимо только отметить его наличие и исключение в аудите.

Метки строятся собственным детерминированным генератором. Стартовый вариант из ТЗ — окно 3+3, разделение событий 4 бара и коэффициент значимости 0,65. Это исходная рекомендация, а не утверждённая разметка.

Будущие точки можно использовать для определения исторической метки `y`, но нельзя показывать модели во входе `X` до их фактического появления. Для события сохраняются его время, время доступности метки и задержка. Неразмечаемые примеры исключаются с указанием причины.

## 5. Проверка качества

### Данные для проверки

Используется хронологическое разделение **train → validation → test**, с общими временными границами для инструментов. На границах исключаются пересечения окон и будущих точек разметки — purging; дополнительный промежуток embargo фиксируется в manifest.

Настройки, признаки и пороги выбираются на train/validation. Test используется для итоговой проверки. Актуальные окна API служат для проверки применения и не заменяют исторический test.

### С чем сравниваем

- **Majority baseline:** всегда самый частый класс, определённый на train.
- **RD-baseline:** причинное правило на доступных значениях RD.
- **ML-модель:** обучение на признаках окна.

Если правило уже полностью решает задачу на доступных данных, необходимость ML должна быть обоснована сравнением.

### Что измеряем

| Метрика | Назначение |
|---|---|
| Macro F1 | Качество с равным весом классов; кандидат на основную метрику |
| Precision, recall и F1 по классам | Ложные обнаружения и пропущенные развороты |
| Balanced accuracy и матрица ошибок | Полнота по классам и характер путаницы |
| Ложные события и задержка | Качество обнаружения во времени |
| Доля пропусков обработки | Доступность корректного результата на входных окнах |

Оценка отдельно рассматривает инструменты, временные участки и рыночные режимы при достаточном числе событий. Результаты классификации окон и обнаружения событий разделяются. Вероятности проверяются на калибровку.

## 6. Полученные данные и текущие результаты

### Как получаем данные

`get_data.py` отправляет GET-запрос к `https://ms.2eng.ru/api/ml/ds/feature-windows` с параметрами `contractVersion=model-window-64x6-v1`, `lookbackSteps=64`, `readyOnly=true`. Логин и пароль читаются из переменных окружения. Запуск из корня проекта:

```bash
uv run --env-file .env python get_data.py
```

Скрипт сохраняет весь ответ в `data/feature-windows_<дата-время-UTC>.json`. При каждом запуске создаётся новый файл. Папка `data/` исключена из Git.

### Что находится в JSON

| Поле | Содержимое |
|---|---|
| `contractVersion`, `timeframe`, `lookbackSteps` | Версия контракта, минутный шаг и длина окна |
| `featureColumns` | Порядок шести чисел в каждой строке |
| `generatedAt` | Время формирования ответа сервером |
| `items` | Список окон по инструментам |
| `items[i].symbol` | Инструмент выбранного окна |
| `items[i].state`, `reason` | Готовность окна и причина неготовности |
| `items[i].pointsCollected`, `expectedPoints` | Собранное и ожидаемое число точек |
| `items[i].windowStartTimestamp`, `windowEndTimestamp` | Время начала и конца окна, Unix-миллисекунды UTC |
| `items[i].features` | Матрица входных значений формы `64 × 6` |

Пример извлечения данных после `data = response.json()`:

```python
item = data["items"][0]        # Первое окно в ответе
X = item["features"]           # Все 64 строки по 6 чисел
latest = X[-1]                 # Последняя строка окна
rd_value = latest[0]           # Последний RD
close = latest[4]              # Последняя цена закрытия
volume = latest[5]             # Последний объём
```

Одна строка, **условные числа для пояснения**, в порядке `rd_value, open, high, low, close, volume`:

```json
[0.2, 100.0, 105.0, 98.0, 103.0, 250.0]
```

### Статистика одного сохранённого ответа

Проверен локальный снимок от **25 октября 2026 года, 17:28 МСК**. Это описание одного ответа, а не всего доступного исторического датасета.

| Показатель | Значение |
|---|---:|
| Окон / уникальных инструментов | 236 / 236 |
| Окон со статусом `READY` | 236 |
| Форма каждого окна | 64 × 6 |
| Всего минутных строк | 15 104 |
| Всего входных чисел | 90 624 |
| Нечисловые или бесконечные значения в `features` | Не обнаружены |

Для всех окон разность конечного и начального timestamp равна 63 минутам, что соответствует границам 64 минутных наблюдений. Проверка структуры не подтверждает свежесть снимка при последующем использовании и не заменяет полный аудит данных. Наличие только READY связано в том числе с фильтром `readyOnly=true`: по этому ответу нельзя судить о доле неготовых инструментов в системе.

### Где находятся таргеты

В JSON **нет правильного ответа `y`**: API отдаёт входные окна. `state=READY` — техническая готовность данных, а не целевой класс.

Для обучения на исторических CSV генератор разметки должен построить **одну метку на окно**: `TURN_UP` (1), `NO_TURN` (0) или `TURN_DOWN` (−1). Правило привязки события к окну ещё предстоит определить. Распределение этих меток нельзя посчитать по текущему JSON без разметки и необходимой истории.

**Качество модели пока не измерено:** обучение не проводилось. Метрики чужих синтетических экспериментов не используются как результат этой модели.

## 7. Ограничения и риски

- Метрики зависят от определения разворота. Совпадение с разметкой не доказывает прибыльность торговли.
- Минутные свечи не сохраняют порядок движений внутри минуты.
- Качество может различаться между инструментами и меняться со временем.
- Ложные сигналы, пропуски и задержка могут ухудшать последующие решения.
- Необходимы проверки соответствия исторического RD актуальному API и достаточности данных по группам.

Доступы хранятся вне кода. Данные заказчика и реальные логи распространяются только с разрешения владельца. Для публичных примеров используются разрешённые агрегаты или синтетика.

## 8. Как будем проверять применение модели

Проверку интеграции планируем выполнять без реальной публикации торговых сигналов. В ТЗ используются следующие термины:

| Термин | Простое объяснение |
|---|---|
| **Fixture — тестовый пример** | Заранее подготовленный JSON с известным содержимым. Позволяет повторяемо проверить правильное окно, WARMUP или ошибку. Может использоваться в разных режимах проверки. |
| **Dry-run — пробный запуск** | Выполнить расчёт и сформировать предполагаемый результат, но не отправлять его в рабочий контур. |
| **Shadow — теневой режим** | Обрабатывать актуальные данные параллельно действующей системе и отдельно сохранять результаты, не влияя на её решения. |

В нашем проекте эти проверки ещё не реализованы. Сейчас `get_data.py` только получает и сохраняет JSON — модель при этом не вызывается.

При WARMUP, устаревании, неверной форме, нечисловых значениях и недостатке данных результат модели не формируется; причина записывается. Повтор окна `symbol + windowEndTimestamp` не должен дублировать публикацию.

Для разрывных окон предварительная политика — пропуск без интерполяции. PDF допускает gaps в READY, а более поздняя инструкция требует пропуска; окончательное поведение нужно уточнить.

При применении сохраняются версия модели и статусы обработки. Обновлённая модель проходит проверку перед заменой предыдущей. Для каждой версии сохраняется соответствующая карточка.
